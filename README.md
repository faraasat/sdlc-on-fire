# SDLC on Fire

**A daemon that will not let the agent lie.**

Coding agents mark their own work done. They report that tests pass, that the change is complete, that the edge case is handled — and the report is generated by the same process that wrote the code, from the same context, with the same blind spots. When it is wrong, nothing downstream can tell.

SDLC on Fire puts a process between the agent and "done". The agent writes the code. A local daemon runs the checks, reads the output, and decides whether the work item may move. There is no flag the agent can pass to skip that.

```console
$ sdlc advance TASK-001
TASK-001: BLOCKED at "implement" (wanted "test")
  ✗ claim-required-to-execute: TASK-001 has no live claim; acquire one before entering "test" (ADR-0048)
  ✗ gate: test failing evidence says the check did not pass — fix the code, then re-verify
```

> **Prerelease `0.1.0-alpha.2`, and it is now what `npm install sdlc-on-fire` gives you** — `latest` was moved onto it once `alpha.0`'s `tiers` defect was fixed. Interfaces change between alphas and [a real slice is unfinished](#what-is-not-built-yet). Kick the tyres; don't build a company process on it yet.

## You do not live in this CLI

Worth saying early, because most tools in this space get it backwards.

**You work where you already work** — Claude Code, Cursor, Copilot, Gemini, OpenCode, or an MCP client. `sdlc` compiles its skills into whatever agent surface you use, and your agent loads them like any other skill. No new chat window, no new editor, no second place to keep things in sync.

```console
$ sdlc skills compile --target claude-code
compiled 5 skill(s) → claude-code
  ✎ .claude/skills/implement/SKILL.md  (4691 bytes)
  ✎ .claude/skills/resolve-conflict/SKILL.md  (6362 bytes)
  ✎ .claude/skills/retrospective/SKILL.md  (2517 bytes)
  ✎ .claude/skills/review/SKILL.md  (5119 bytes)
  ✎ .claude/skills/spec/SKILL.md  (4713 bytes)
```

One canonical source, six targets. Change a skill once and recompile; you are not maintaining six copies by hand and discovering the drift later.

The CLI is the **spine**, not the interface. You touch it to ask what happens next —

```console
$ sdlc instructions FEAT-001
FEAT-001 — CSV export for reports
  stage:  discovery (standard/feature)
  next:   spec
  skill:  spec → spec_output
  tokens: ~110 (98 cacheable, 89%)
```

— and to let the daemon check the work. Everything in between happens in your agent, in your editor, in the loop you already have.

And notice what the compiled skills deliberately do **not** contain: any instruction to run the tests and report the result. A skill that says _"run the suite and tell me how it went"_ has handed grading back to the thing being graded. The `implement` skill says the opposite in as many words — _"Do not report that tests pass — the daemon runs verify and reads the output itself."_

## Install

```bash
npm install -g sdlc-on-fire
```

Node 20 or newer. The first `sdlc init` provisions a local PGlite database inside the workspace — no Docker, no connection string, nothing to configure.

## What a run actually looks like

Everything below is real terminal output, copied from a scratch workspace, not an illustration.

**Scaffold a workspace.** It never overwrites a file that already exists, so it is safe to run in a repo that already has a `README.md`.

```console
$ sdlc init
Workspace initialised.
  root:    /tmp/demo
  created: 30 file(s)
  skipped: 0 existing file(s)
  db:      PGlite ready
```

**Create a work item.** It lands in `kanban/_inbox/` as a Markdown file with typed frontmatter — git-tracked, diffable, editable in any editor.

```console
$ sdlc new task "Add CSV export"
Created TASK-001 at /tmp/demo/kanban/_inbox/TASK-001.md
```

**Run its checks.** The card declares its own `verify:` command. The daemon executes it and reads the output — this is the part an agent never gets to do on its own behalf.

```console
$ sdlc verify TASK-001
TASK-001: passed (2/2 tests)
  command:  node --test --test-reporter=tap test.js
  exit:     0  (71ms)
  evidence: #2 recorded by the daemon, not claimed by an agent
```

**Exit 0 is not "tests passed", and the tool says so.** Point it at a command with no machine-readable output and it records what it actually observed, at reduced confidence, with the fix:

```console
$ sdlc verify TASK-001
TASK-001: exited 0 — no test report was parsed, so no test count was observed
  command:  node test.js
  exit:     0  (28ms)
  evidence: #1 recorded by the daemon, not claimed by an agent
  ⚠ no test count could be read — this is exit-code-only evidence (confidence 0.6).
    Add a machine-readable reporter to the verify command (e.g. `--reporter=json`
    for Vitest/Jest, or `--test-reporter=tap` for node:test) to record real counts.
```

**Break the code and the gate closes.** `advance` exits non-zero, so CI can depend on it:

```console
$ sdlc verify TASK-001
TASK-001: FAILED (exit 1)

$ sdlc advance TASK-001
TASK-001: BLOCKED at "implement" (wanted "test")
  ✗ gate: test failing evidence says the check did not pass — fix the code, then re-verify
```

**Fix it, and the same command moves the item.** Nothing was asked to reconsider; the evidence changed.

```console
$ sdlc verify TASK-001
TASK-001: passed (2/2 tests)

$ sdlc advance TASK-001
TASK-001: implement → test
```

Every command has a `--json` twin.

## The ideas it is built on

**Evidence is bound to a commit.** A passing run recorded against one tree says nothing about a different tree. Edit a file after the suite passed and the evidence goes stale — the gate notices, and asks for a re-run rather than accepting a result that describes code no longer on disk.

**Markdown in git is the source of truth; the database is a rebuildable mirror.** Everything the tool knows about your work items survives `sdlc db:rebuild` from the files alone. Delete the database directory and nothing is lost. This is a hard rule, not a preference: no feature is allowed to make the database authoritative for content.

**Agents are actors, never approvers.** Where a human sign-off is required — a security review on an auth change, a rescope approval to insert work into a live sprint — the check is on the actor's _kind_, not on a role name. A role can be granted to a service account. "Is this a human" cannot be argued with.

**Where a model decides something, a deterministic checker disposes of it.** The merge-conflict assistant explains what each side of a conflict was for, which is genuinely useful and genuinely unverifiable. So the explanation is recorded and never checked, while three mechanical questions decide whether the resolution is accepted: are the markers gone, was a side silently dropped, and did the tests re-run _after_ the resolution.

## What is in the box today

| Area             | What works                                                                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lifecycle        | Data-driven stage machine, three presets (`lite`/`standard`/`strict`), per-work-type stage ladders, claim/lease so two actors cannot own one item               |
| Evidence & gates | Daemon-executed verify, test-output parsers, commit-bound staleness, three-way gate verdicts (failed / missing / abstained — never collapsed to pass/fail)      |
| Context          | Task-scoped context packs, hybrid retrieval (BM25 + vector + RRF), per-stage token budgets, cache-aware prompt ordering                                         |
| Security         | Dependency install gate with typosquat and advisory checks against live OSV data, secret scanning, prompt-injection detection, high-risk-surface review routing |
| Git              | Branch-per-work-item, PR bodies rendered from the recorded evidence bundle, revert-reintroduction guard, merge-conflict review                                  |
| Insertion        | Cheap capture, hard insertion with blast-radius analysis and rescope approval, selective gate re-open                                                           |
| Imports          | Reads existing specs and plans from other agent tooling into the workspace                                                                                      |

Run `sdlc --help` for the full command list; there are about forty.

## What is not built yet

Named plainly, because a roadmap presented as a feature list is how tools lose people's trust:

- **No UI.** Kanban is a directory of Markdown files. The web interface is a later phase.
- **No RBAC.** Roles exist in the object model and are not enforced. Single-operator only.
- **No long-running daemon.** "The daemon" is the CLI doing the work in-process. `sdlc verify` runs your command right now; nothing is watching in the background yet.
- **One agent surface.** Skills compile to Claude Code. Codex and MCP targets are designed and not finished.
- **Not validated outside its own repo.** It is used to build itself, which catches a great deal and is not the same as being used by someone else.

## Development

Requires Node ≥ 20 and pnpm ≥ 9 (`corepack enable` is enough — the repo pins the version).

```bash
pnpm install
pnpm check     # format:check → lint → typecheck → test → build
```

| Script                      |                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| `pnpm build`                | `tsc --build` emits declarations, `tsup` emits the bundle, per package in dependency order |
| `pnpm test`                 | Vitest across every package; cross-package imports alias to source, so no build step first |
| `pnpm typecheck`            | `tsc --build` over the project-reference graph                                             |
| `pnpm lint` / `pnpm format` | ESLint with type-checked rules / Prettier                                                  |
| `pnpm verify:package`       | Packs every package and checks the tarballs are actually installable                       |
| `pnpm changeset`            | Records a release note; all packages version in lockstep                                   |

Tests run against real systems rather than mocks wherever it is affordable — real PGlite, real git repositories, real tarballs, and the live OSV advisory API. A stub can only confirm the shape you already believed.
